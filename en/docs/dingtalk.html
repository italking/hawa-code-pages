DingTalk

DingTalk integration lets Hawa Code listen to DingTalk message events (message, reaction, read, recall) and, once reply is enabled, reply to DingTalk conversations directly — a two-way loop.

It is provided by the built-in MCP server @dahawa/hawa-channel. Notifications are injected through the Channel protocol, and authentication is delegated to the DingTalk CLI dws (using the current user’s OAuth login — no AppKey/AppSecret required).

What It Does

  • Listen: messages that @ you, direct chats, group messages, reactions, reads and recalls are injected into the agent context in real time.
  • Reply: after receiving an event, the agent can call the MCP tool to send the answer back to the corresponding direct chat or group.

Prerequisites

  • Node.js ≥ 20.
  • Install the DingTalk CLI dws and complete OAuth login for the current user:

On startup hawa-channel automatically checks dws availability and login status. It exits with an error if not logged in — it never fails silently.

Enabling

Add the following to the .mcp.json of your hawa-code project:

Webhook and DingTalk can be toggled independently (WEBHOOK_ENABLED=false means no WEBHOOK_SECRET is needed).

Environment Variables

Variable Default Description
DINGTALK_ENABLED false Start the DingTalk event listener
DINGTALK_LISTEN_KIND at-me Listen scope, see the table below
DINGTALK_EVENTS message Comma-separated: message / reaction / read / recall
DINGTALK_USER_QUERY none Required when kind=sender — user query condition
DINGTALK_CHAT_QUERY none Required when kind=group — chat query condition
DINGTALK_SENDER_FILTER none Sender whitelist, comma-separated (names or openDingtalkIds), see the section below
DINGTALK_SEND_ENABLED false Register the send_dingtalk_message reply tool
DWS_BIN dws dws executable name or absolute path
DWS_PROFILE none dws profile; listening and replying must use the same one
LOG_LEVEL info debug / info / warn / error

Listen Scope (LISTEN_KIND)

kind Scope Allowed events
at-me Messages that @ the current user (default) message only
all-direct All direct chat messages message only
all-group All group messages message only
sender A specific user — requires DINGTALK_USER_QUERY All four event kinds
group A specific chat — requires DINGTALK_CHAT_QUERY All four event kinds

Sender Whitelist (SENDER_FILTER)

DINGTALK_LISTEN_KIND=sender can only resolve one sender via DINGTALK_USER_QUERY. To listen to multiple specific senders at once, combine all-direct (all direct chats) with a whitelist — hawa-channel filters messages by sender before injecting them into the agent:

With the configuration above, all direct chat messages are received, but only those sent by Zhang San, Li Si, or that openDingtalkId are injected into the agent — the rest are discarded inside hawa-channel.

  • The list is comma-separated; entries can be sender names or openDingtalkIds — a match on either lets the message through. In production, prefer openDingtalkIds to avoid mismatches caused by duplicate names.
  • When the whitelist is empty (not configured), no filtering occurs and all direct chat messages from all-direct are injected.
  • The whitelist applies to every LISTEN_KIND (not just all-direct), but all-direct / at-me / all-group themselves only support message events.
  • Changes to the list require restarting the MCP server to take effect; filtered-out messages can be seen in LOG_LEVEL=debug logs.

What the Agent Receives

Events are normalized into a unified format before being injected:

Event Injected body example (actual format)
message [钉钉消息] 张三: please check the build log
reaction [钉钉 reaction] 张三: 赞
read [钉钉已读] 张三: msg_xxx
recall [钉钉撤回] 张三: msg_xxx
  • Non-text messages are rendered with type labels: [图片] / [语音] / [视频] / [文件] / [位置] / [链接] / [富文本] (image / voice / video / file / location / link / rich text).
  • meta carries messageId, sender, chatId, msgtype, timestamp, etc. The agent can use conversationId or senderOpenDingtalkId from the event to target its reply.

Replying to DingTalk (send_dingtalk_message)

Reply is disabled by default (to prevent the agent from accidentally sending messages outward). The tool is only registered after explicit opt-in:

Tool parameters:

Parameter Required Description
content Yes Reply text, 1–4000 characters after trimming
conversationId One of the two Conversation ID (group or direct), from the event meta
userOpenDingtalkId One of the two User open ID, from the event meta

Exactly one of the two target parameters must be provided. The tool calls dws chat +messages-send --as user under the hood; whether a permission prompt appears depends on hawa-code’s own tool permission settings.

Troubleshooting

Symptom Investigation
Startup error dws OAuth is not logged in Run dws auth login to complete OAuth; check DWS_BIN and DWS_PROFILE
No events arriving Check LISTEN_KIND, user/chat query conditions, and event types; dingtalk listener ready in the logs means the listener is ready
Listener restarts frequently This is normal reconnect behavior (exponential backoff + dws subscription status check); if it keeps failing, inspect dws stderr with LOG_LEVEL=debug
tools/list has no reply tool Confirm DINGTALK_SEND_ENABLED=true and reconnect the MCP server
No logs hawa-channel writes runtime logs to stderr (MCP stdout carries only the protocol); raise LOG_LEVEL

How It Works

  • No custom protocol: it reuses the dws event +listen-im long connection to subscribe to IM events. Subscription management and self-loop filtering are handled by dws; hawa-channel only consumes the NDJSON event stream from its stdout and normalizes the fields.
  • Delegated authentication: it uses the current user’s dws OAuth (open-source normal mode — no AppKey/AppSecret). hawa-channel never touches or stores any DingTalk secret; credentials are saved by dws itself under ~/.dws.
  • Resilience: the process reconnects automatically with exponential backoff after exit. Before reconnecting it queries dws event status and respects dws’s subscription protection (no forced re-subscription during the cooldown window).
  • Unified egress: after normalization, everything is injected via the MCP notification notifications/hawacode/channel with source=dingtalk. Replies go in the reverse direction through the MCP tool calling dws — the whole path never touches a shell.
