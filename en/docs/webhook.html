Webhook

Webhook is Hawa Code’s generic inbound channel for external events: any system capable of sending HTTP requests (CI, monitoring, Git platforms, scheduled jobs, custom services) can push events into the agent’s conversation context in real time — no polling required.

It is provided by the built-in MCP server @dahawa/hawa-channel and injects notifications through the Channel protocol.

What It Does

Typical scenarios:

  • CI build success / failure alerts
  • Monitoring alerts
  • Git platform PR / Issue events
  • Async notifications from any custom system

::: warning
When WEBHOOK_ENABLED=true (the default), WEBHOOK_SECRET is required — startup fails without it.
:::

Environment Variables

Variable Default Description
WEBHOOK_ENABLED true Enable the webhook HTTP receiver
WEBHOOK_HOST 127.0.0.1 Listen address; change to a server IP or 0.0.0.0 to expose it
WEBHOOK_PORT 9527 Listen port
WEBHOOK_SECRET none HMAC signing secret — used only for verification, never log it
WEBHOOK_ALLOWED_IPS empty Comma-separated client IP allowlist; empty means no restriction
LOG_LEVEL info debug / info / warn / error

Webhook and DingTalk are independent features and can be toggled separately.

Sending Requests

Endpoints

channel may contain only lowercase letters, digits, underscores and hyphens (^[a-z0-9_-]{1,32}$). Use it to distinguish event sources, e.g. ci, monitor, git.

Headers

Header Required Description
Content-Type Yes Must be application/json
X-Timestamp Yes Unix timestamp in seconds
X-Signature Yes sha256= + 64 hex chars (HMAC)

Signature Algorithm

The signature is computed over the raw request body. Any JSON reformatting (extra whitespace, changed field order) breaks verification — sign first, then send the body unchanged.

Requests whose timestamp differs from server time by more than 5 minutes are rejected. Duplicate requests with the same channel + timestamp + body are blocked by replay protection.

Request Body

Any JSON object. The notification text is extracted with priority text → message → content; if none of them exists, a compact JSON string is used. An event field is passed to the agent as metadata.

Response Codes and Troubleshooting

HTTP Status Meaning
400 Invalid channel, Content-Type, request JSON or Content-Length
401 Missing / wrong timestamp or signature, timestamp outside the 5-minute window, replayed request
403 Client IP not in the allowlist
404 Path or method mismatch
413 Request body exceeds 1 MiB
429 Per-channel rate limit exceeded (60 requests / minute)
500 Internal server error

Troubleshooting tips:

  • Startup error about missing WEBHOOK_SECRET: set the environment variable and restart hawa-code.
  • Persistent 401: verify the secrets match, the timestamp is in seconds, and the signature is computed over the raw request body.
  • 403: check whether WEBHOOK_ALLOWED_IPS contains the client address.
  • Notifications not arriving: hawa-channel logs to stderr (MCP stdout carries only the protocol); raise LOG_LEVEL=debug for details.

How It Works

  • Signature verification: HMAC-SHA256(secret, timestamp + "." + rawBody) — the shared secret lets the sender prove and the receiver verify; the key itself never travels over the network.
  • Freshness and replay protection: a 5-minute timestamp window plus an in-memory replay cache blocks stale requests and verbatim replays.
  • Protection mechanisms: per-channel token-bucket rate limiting (60/min), a 1 MiB body limit, and an optional IP allowlist.
  • Async processing after ACK: HTTP 200 is returned first; the message is then normalized and pushed to hawa-code through the MCP notification notifications/hawacode/channel, so external systems are never blocked by slow agent processing.
