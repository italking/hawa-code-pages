Headless

Headless Help Documentation

Headless mode lets Hawa Code run without launching the terminal interactive interface, making it suitable for UI-less environments, remote services, and automation scenarios. Note that Headless is NOT enabled via a --headless parameter. Hawa Code provides two UI-less ways of running:

  1. hcode server: Headless resident service. The process stays running without rendering a terminal UI, with a built-in WebServer (HTTP + WebSocket) for remote control via browser. This is the official Headless run mode.
  2. hcode -p "...": Single-turn non-interactive mode. Executes one task, prints the result to standard output, and exits. Suitable for pipes and script invocation, but not a resident service.

Note: The headlessBrowser setting (headless browser) is used for web page fetching and rendering, and is unrelated to the Headless run mode. Do not confuse the two.

1. Differences Between the Two Modes

Comparison hcode server hcode -p "..."
Run mode Process stays resident, does not exit Exits after a single run
Interactivity Real-time interaction in browser, tool-call approval No interaction, one-shot output
Use cases Remote resident services, UI-less environments CI/CD, scripts, pipe invocation
  • Use hcode server when you need to “run long-term on a remote machine and use the full Agent capability via browser”.
  • Use hcode -p when you need to “run a single command in a pipeline and judge the result by exit code”.

2. Starting the Headless Service with hcode server

2.1 Command Format

A standalone dist entrypoint is also provided, which launches the build output directly with node and takes the same parameters as hcode server:

2.2 Parameters

Parameter Description
--resume <id> Resume a historical session (matching the full log path or file name suffix <id>.jsonl); exits with code 1 if not found
--cwd <path> Working directory, defaults to the process’s current directory
--verbose Verbose output
--dangerously-skip-permissions Skip all permission confirmations; carries security risks, see Notes

The WebServer is fully driven by settings (settings.webServer.enabled, etc.); command-line overrides such as --port / --host / --token have been removed. Configure the port and bind address in settings; the default bind address is 0.0.0.0. Make sure webServer.enabled is turned on in settings before using hcode server; if it is not enabled, the process still starts but only prints a Hawa Code headless server started (WebServer disabled, set settings.webServer.enabled=true to enable) hint without starting the WebServer.

2.3 Login and Authentication

The Web UI now uses username + password login authentication (the --token parameter is no longer used), with a built-in login page:

  • Default credentials: admin / admin when unconfigured; not persisted to disk. Change them as soon as possible after first login.
  • Credential storage: Saved as a scrypt hash in user-level settings (webServer.username / passwordHash / authSalt in ~/.hcode/settings.json).
  • Where to change: the Web Server username/password items in terminal /config, or “Settings → Account” in the Web UI (requires the current password).
  • Session token: After login, the server issues an HMAC-signed token valid for 7 days; HTTP requests pass it via Authorization: Bearer <token>, and the WebSocket handshake passes it via subprotocol or ?token=. Changing the password invalidates old tokens immediately; re-login is required.
  • Endpoints: GET /api/auth/status (login status), POST /api/auth/login (login to obtain a token), POST /api/auth/change-password (change credentials); other /api/* and /ws requests return 401 without a valid token.
  • Logging in with default credentials shows a warning banner in the Web UI; binding to a non-loopback address with default credentials prints a weak-password warning at startup.

2.4 Examples

2.5 Running in the Background

Run resident in the background on a Linux/macOS server (logs written to a file, standard input redirected to avoid blocking):

  • Standard input must be redirected to /dev/null (or set CI=true), otherwise pipe scenarios block startup while waiting for EOF.
  • Startup output and errors go to hcode-server.log; session logs still live under UCODE_ROOT_DIR/projects/<project directory>/.
  • Stop the service: pkill -f "cli.js server" (match the actual process command line; after the hcode shim is exec’d, the command line no longer contains “hcode”, so "hcode server" won’t match), or simply kill <PID>.
  • For production, systemd or Docker is recommended, see Section 6.

3. Prerequisites

  1. Complete terminal-mode initialization first: Headless mode skips terminal-interaction-dependent steps such as Onboarding, the trust dialog, and MCP approval. Please run hcode once in terminal mode first to complete initialization configuration such as model/API.
  2. Model and API configuration: Make sure the model and API have been configured via terminal mode and are valid; startup or queries will report errors if the configuration is invalid.
  3. Login credentials: The Web UI logs in with username + password. Before exposing the service on a non-loopback address, change the default credentials (admin/admin) via terminal /config or the Web UI settings to avoid weak-password exposure.
  4. Working directory: The process automatically grants read permission to the --cwd directory, without terminal trust confirmation.

4. How to Tell If Startup Succeeded

Signs of a successful startup:

  1. Hawa Code headless server starting... and Tools, commands and MCP clients loaded, starting Web server... appear on standard output in sequence.
  2. Followed by Hawa Code headless server started and the access URL (e.g., URL: http://0.0.0.0:3210) plus startup timing. The actual port is subject to the URL: line in the startup output (already incremented by 1 on port conflict).
  3. The process stays resident and does not exit; open the URL in a browser and log in to use it.

After a session starts, session content is no longer printed to terminal standard output; session messages are persisted as JSONL and pushed to the browser in real time via WebSocket. The process supports graceful shutdown via SIGINT/SIGTERM (kill <PID> exits cleanly).

5. Logs and Troubleshooting

Logs are located under UCODE_ROOT_DIR/projects/<project directory>/:

Path Content
messages/*.jsonl Session message records
log/*.log Runtime logs
log/error-<date>.log Error logs
errors/*.txt Error records
mcp-logs-<server>/ Logs of each MCP Server

Common failure signals and exit codes:

Symptom Description
Failed to start WebServer: ... and exits with code 1 WebServer failed to start, commonly due to port occupied, webServer.enabled not turned on in settings, etc.
WebServer not ready within 30 seconds serverRunner timed out waiting for the WebServer to become ready; check the webServer settings and port occupation
Session log not found: <id> and exits with code 1 The session log specified by --resume does not exist
Process killed or exits after successful startup Abnormal; check the error logs

Suggested troubleshooting order: check the hints in standard output → inspect log/error-*.log → check whether the browser is logged in (unauthenticated access to /api/* and /ws returns 401) → check MCP logs if necessary.

6. CI/CD and Script Scenarios

  • Prefer hcode -p: Executes one query, prints the result to standard output, and exits with code 0, suitable as a CI step judged by exit code.

    The process exits with code 1 when standard input has no content.

  • Use hcode server for resident remote services / UI-less environments: runs resident on servers, Docker, systemd, with the browser as the frontend.

  • Batch and automation tasks: Call POST /api/auth/login first to obtain a session token, then submit tasks programmatically via the WebServer REST / WebSocket API (requests must carry Authorization: Bearer <token>).

7. Notes

  1. Permission confirmations require someone to approve in the browser: In Headless mode, the Web client is the only approval channel; tool confirmations time out after about 5 minutes if no client responds.
  2. Security risks of --dangerously-skip-permissions: This parameter skips all permission confirmations, and the Headless path does not perform the isolated-environment check from terminal mode. Use it only in trusted, isolated environments.
  3. Mind standard input when running in the background: Running in the background via systemd, docker run -d, etc. is unaffected; but pipe/heredoc scenarios (e.g., somecmd | hcode server) block startup while waiting for stdin EOF. When running in the background, make sure standard input is /dev/null or set CI=true.
  4. Port conflicts are handled automatically: On port occupation, the port is incremented by 1 automatically; the actual port is subject to the URL: line in the startup output.
  5. Login credential security: Credentials are stored as a scrypt hash in user-level settings, but the default credentials (admin/admin) are publicly known and only suitable for local experimentation. Always change them before any external exposure; changing the password invalidates existing session tokens immediately.
  6. Other limitations: No built-in task timeout or failure retry; the integrity of cross-session recovery via --resume has not been fully validated; the Headless path does not execute SessionStart hooks — users relying on that hook to inject context should take note.
